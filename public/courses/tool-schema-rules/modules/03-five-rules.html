5 条规则，逐条拆解

每条都是「反例 → 正例」的对照，外加一道应用题

规则 1

枚举优先：能用 enum 就别写 description

还记得模块一的 88/88 → 0/89 吗？这就是它的落地写法：

❌ 反例 

"status": {
  "type": "string",
  "description": "订单状态，如已完成、
    待支付等"
}
// 模型自由发挥："completed"
// "paid"、"done" 都可能出现
✅ 正例 

"status": {
  "type": "string",
  "enum": ["pending", "paid",
    "shipped", "closed"]
}
// 模型只能四选一，
// 想错都没有机会
应用题

你在给一个「发送邮件」工具写 schema，priority 参数希望模型填 high / normal / low 之一。怎么写？

priority 参数的正确写法是？

规则 2

约束下沉：格式写进 pattern/format，别靠「请确保」

❌ 反例 

"date": {
  "type": "string",
  "description": "请确保使用
    YYYY-MM-DD 格式"
}
// prose 约束是建议，不是边界
✅ 正例 

"date": {
  "type": "string",
  "format": "date",
  "pattern": "^\\d{4}-\\d{2}-\\d{2}$"
}
// 机器可校验：
// 111/111 诚实报错的那一类
💡
检测口诀

看到 description 里有「请确保」「必须」「不能超过」——警报响起：这句话该搬家到机器可校验的字段里去。

规则 3

一词一义：名字里不许有歧义缩写

❌ 反例 

{ "name": "get_usr_info",
  "parameters": {
    "uid": "用户ID或用户名",
    "ts": "时间范围或时间戳"
  } }
// usr 是 user 还是用户组？
// ts 接受几种形态？模型只能猜
✅ 正例 

{ "name": "get_user_profile",
  "parameters": {
    "user_id": "唯一数字ID",
    "timestamp": "ISO 8601 时间戳"
  } }
// 一词一义，无从猜错

一个参数描述里出现「或」字，就是幻觉参数的温床——模型猜错分支，比猜错值更难排查。

规则 4

错误设计：报 422 + 结构化错误，别报 200 + 模糊文案

❌ 反例 

HTTP 200
{ "code": 0,
  "msg": "ok",
  "data": null }
// agent 无从分支：
// 是没命中，还是没理解？
// 41% 虚报成功率的源头
✅ 正例 

HTTP 422
{ "error": {
    "field": "date",
    "constraint": "pattern",
    "expected": "YYYY-MM-DD",
    "received": "09/04/2026" } }
// agent 拿到修复所需的全部信息
🔧
为什么重要

结构化错误是 agent 重试和自我修复的触发信号。「expected vs received」让模型一眼看出差在哪，下一轮就能改对。

规则 5

描述有界：description 只写语义，不承载约束

❌ 反例 

"count": {
  "type": "integer",
  "description": "返回条数，不能超过100，
    必须是正数，否则请求无效"
}
// 约束藏在散文里 = 没有约束
✅ 正例 

"count": {
  "type": "integer",
  "minimum": 1,
  "maximum": 100,
  "description": "单页返回条数"
}
// 语义归语义，约束归机器
