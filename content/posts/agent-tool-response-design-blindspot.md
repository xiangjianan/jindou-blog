# 你的 Agent 在对失败装瞎：工具响应设计的盲区

## 一个让我们沉默的实验结果

我们做了一个受控实验（40 个 trial，qwen2.5:7b，schema 形式化梯度 L0→L3），给模型一个查询类工具，然后在「silent 注入」条件下让 API 返回 HTTP 200 + 空结果/无关数据。结果是：**无论 schema 写得多规范——从纯 prose 描述到 L3 级语义约束——静默失败率都是 100%（5/5 × 4 个档位）**。模型拿到 200 + 空数组，没有一次停下来怀疑，全部把它当成功处理并向用户汇报。Schema 形式化档位之间的趋势检验 p = 0.5，逐对比较全部无效。换句话说：我们在请求侧投入的所有形式化努力，对响应侧的盲区贡献为零。

## 盲区在哪：请求侧 vs 响应侧

这暴露了一个被整个工具生态忽视的不对称：我们花了大量精力告诉模型「参数该怎么填」——枚举、正则、范围、JSON Schema 约束——但从没告诉它「响应该怎么读」。模型的诚实性被请求侧 schema 训练和约束得很好，但响应侧是一片没有语义地标荒原：`200 OK` + `{"results": []}` 到底是「没找到」还是「查询没被理解」还是「后端挂了但网关兜底」？对模型来说这些全部长一个样。

文献也支持这个划分：SilentProbe（arXiv:2609.00035）发现机器可校验的请求约束 111/111 返回诚实错误，而只写在文档散文里的约束 44/61 静默失败——说明请求侧的诚实性靠 schema 形式化可以修复。但响应侧没有任何等价机制。失效谱系里最难的两级——静默失败和虚报成功——都发生在响应读取环节。

## 四条工具响应设计规则

**规则 1：语义状态字段。** 响应体显式携带 `status`，别让模型从空数组猜。

```json
// 反例
{"results": []}
// 正例
{"status": "no_match", "results": [], "matched_count": 0}
```

**规则 2：错误即错误。** 查无结果不是成功，别用 200 + 空体伪装成功。

```json
// 反例：HTTP 200
{"results": []}
// 正例：HTTP 404
{"error": {"code": "USER_NOT_FOUND", "message": "no user matches query 'zhang san'"}}
```

**规则 3：计数显式化。** 用明确的数量字段，让模型可以分支判断。

```json
// 反例
{"data": []}
// 正例
{"matched_count": 0, "data": []}
```

**规则 4：结构一致性。** 同一工具的边界情况返回结构要稳定，不要有时空列表、有时 `null`、有时直接空体。模型学到的是模式，模式漂移一次，它对下一次的解读就会漂移。

```json
// 反例：三种边界三种形状
{"data": null}        // 情况 A
{}                    // 情况 B
{"data": []}          // 情况 C
// 正例：始终同构
{"status": "no_match", "matched_count": 0, "data": []}
```

## 从 schema 到响应：下一步

回到我们的实验结论：**参数约束的形式化解决请求侧诚实性，响应语义的显式化才是解决响应侧盲区的钥匙。** 这两件事是正交的，缺一不可。SilentProbe 证明了提升请求约束只需一行改动就能把失败从 88/88 降到 0/89；我们的实验补上了另一半——响应侧的 100% 静默失败，schema 再好也救不了。

这对 MCP 生态是一个直接的行动号召：MCP 统一了工具的请求协议，但几乎没约束响应语义。如果 MCP 在工具响应规范层面强制要求语义状态字段和错误码（哪怕是「推荐字段」级别），整个生态的 agent 可靠性会跨过一道门槛。在此之前，每一个给 Agent 写工具的开发者，都应该问自己一句：我的工具在「没找到」的时候，返回的东西能让模型分辨出失败吗？
